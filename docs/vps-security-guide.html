1. Your Current Setup — Context

You have a VPS from Strato hosted in Sweden, running Ubuntu. On this server you have two databases:

  • PostgreSQL — your main relational database, accessed via Prisma ORM
  • Redis — an in-memory store used for caching/sessions

You currently store SSH private keys in a folder on your developers' machines (with chmod 700 on the folder and chmod 600 on the key files). The keys are used to create SSH tunnels to the VPS so that Prisma/Redis can connect as if the database were local.

Current architecture: Developer laptop Strato VPS (Sweden) ┌──────────────────────┐ ┌────────────────────────────────┐ │ Prisma / app code │ │ PostgreSQL (port 5432) │ │ ↓ │ │ Redis (port 6379) │ │ SSH tunnel │──SSH──▶│ sshd (port 22) │ │ localhost:5432 ───▶ │ │ │ │ localhost:6379 ───▶ │ │ Auth keys: /etc/ssh/keys/ │ └──────────────────────┘ │ chmod 700/600 ✓ │ └────────────────────────────────┘
ℹ️ What is an SSH Tunnel?

An SSH tunnel (also called port-forwarding) creates an encrypted channel over SSH. Your app thinks it's talking to localhost:5432, but SSH secretly forwards all that traffic to your-vps:5432 through an encrypted connection. It works, but it's fragile — tunnels drop when your SSH connection drops, and there's no automatic reconnection without tools like autossh.

2. Why Move Away from SSH Tunnels?

SSH tunnels are a valid approach, but they have real downsides in production:

Problem Impact How often it bites you
Tunnel drops silently App loses DB connection; often requires manual restart Very common on long-running processes
Key management complexity Every developer needs a copy of the key; rotating keys is painful Whenever someone joins/leaves the team
Tunnel is per-session CI/CD pipelines, cron jobs, and background workers all need their own tunnels Every deployment
Port 22 (SSH) stays exposed SSH is the most-attacked port on the internet; constant brute-force attempts Every minute (check fail2ban logs)
No built-in mutual auth for apps If an attacker steals the SSH key, they have full shell access to the VPS Key theft/leakage
⚠️ Your specific risk

The chmod 700/600 setup you described is good practice. But if a developer machine gets compromised, the attacker gets full SSH shell access to your VPS — not just database access. This is a much larger blast radius than you want.

3. Your Three Options Explained

Option A: Keep SSH tunnels but harden them (Low effort, medium security)

You can keep using SSH tunnels but improve them significantly: disable password login, use autossh for auto-reconnect, and restrict the SSH key so it can only do port-forwarding (no shell access). This is a quick win but doesn't fully solve the fragility problem.

Option B: Tailscale VPN (Recommended — Low effort, high security)

Tailscale is a free, managed VPN built on top of WireGuard. You install a small agent on your VPS and each developer machine. After that, every device gets a private IP address in your network (e.g., 100.x.x.x). Your app can then connect directly to 100.x.x.x:5432 without any tunnel. No key management, no dropped connections — it just works.

  • ✅ Free for up to 100 devices
  • ✅ No server infrastructure to manage
  • ✅ Works behind NAT/firewalls
  • ✅ Mobile apps available
  • ⚠️ Relies on Tailscale's coordination servers (you trust a third party)

Option C: Self-hosted WireGuard VPN (More effort, maximum control)

WireGuard is a modern, extremely fast VPN protocol built into the Linux kernel since 5.6 (Ubuntu 20.04+). You run a WireGuard server on your VPS. Each developer generates a key pair and gets added to the server's config. All DB traffic goes over the encrypted VPN tunnel — no SSH needed.

  • ✅ 100% self-hosted, no third-party trust
  • ✅ Kernel-level performance (much faster than OpenVPN)
  • ✅ Can close ALL other ports (including port 22)
  • ⚠️ Requires some Linux networking knowledge to set up
  • ⚠️ You manage key generation and distribution yourself

4. Our Recommendation: Start with Tailscale

Since neither of you are DevSecOps professionals, we recommend Tailscale as your first step. Once you're comfortable, you can migrate to self-hosted WireGuard for maximum control. Tailscale is used by thousands of startups and is genuinely easy.

Step-by-step: Tailscale Setup

1

Create a free Tailscale account

Go to tailscale.com and sign up (you can use Google or GitHub login). The free tier supports up to 100 devices — more than enough for your team.

2

Install Tailscale on your VPS

SSH into your Strato VPS and run these commands:

# Add the official Tailscale APT repository
curl -fsSL https://pkgs.tailscale.com/stable/ubuntu/focal.gpg | \
  sudo apt-key add -
curl -fsSL https://pkgs.tailscale.com/stable/ubuntu/focal.list | \
  sudo tee /etc/apt/sources.list.d/tailscale.list

# Install
sudo apt-get update
sudo apt-get install -y tailscale

# Start Tailscale and authenticate
# This prints a URL — open it in your browser to approve the VPS
sudo tailscale up
ℹ️ Why those commands?

curl ... | apt-key add adds Tailscale's cryptographic signing key to Ubuntu's package manager, so Ubuntu trusts packages from Tailscale's server. tailscale up starts the agent and gives you a login URL. After you open the URL and log in, your VPS appears in your Tailscale admin console.

3

Install Tailscale on each developer's machine

  • macOS: Download from the Mac App Store (search "Tailscale") or run brew install tailscale
  • Windows: Download the installer from tailscale.com/download
  • Linux: Same curl | apt-key commands as above

After installing, click "Log in" in the Tailscale menu bar icon and log in with the same Tailscale account. Both devices now appear in your admin console.

4

Find your VPS's Tailscale IP address

On the VPS, run:

tailscale ip -4
# Output example: 100.64.0.5

This 100.x.x.x address is your VPS's private Tailscale address. Only devices on your Tailscale network can reach it — the internet cannot.

5

Update your connection strings

Replace localhost with your VPS's Tailscale IP in your app:

# .env.local (or wherever you store secrets)
# Before (SSH tunnel):
DATABASE_URL="postgresql://user:pass@localhost:5432/mydb"
REDIS_URL="redis://localhost:6379"

# After (Tailscale VPN):
DATABASE_URL="postgresql://user:pass@100.64.0.5:5432/mydb"
REDIS_URL="redis://100.64.0.5:6379"

The 100.x.x.x IP is stable — it doesn't change even if your VPS reboots. You no longer need to open a tunnel before starting your app.

6

Configure PostgreSQL to listen on the Tailscale interface

By default, PostgreSQL only listens on localhost. You need to tell it to also listen on the Tailscale IP:

# Open PostgreSQL config
sudo nano /etc/postgresql/*/main/postgresql.conf

# Find and change this line:
# listen_addresses = 'localhost'
# To:
listen_addresses = 'localhost,100.64.0.5'
# (use your actual Tailscale IP)

Then edit pg_hba.conf to allow connections from the Tailscale subnet:

sudo nano /etc/postgresql/*/main/pg_hba.conf

# Add this line (Tailscale uses 100.64.0.0/10 range):
host    all    all    100.64.0.0/10    scram-sha-256

Restart PostgreSQL:

sudo systemctl restart postgresql
ℹ️ Why pg_hba.conf?

PostgreSQL has a two-layer auth system. postgresql.conf controls which network interfaces PostgreSQL listens on. pg_hba.conf (Host-Based Authentication) controls who can connect from where. The line we added says: "For connections coming from the Tailscale subnet (100.64.0.0/10), require a username/password using SCRAM-SHA-256." This is the most secure password hashing method PostgreSQL supports.

7

Configure Redis to listen on the Tailscale interface

sudo nano /etc/redis/redis.conf

# Find and change:
# bind 127.0.0.1 -::1
# To (add the Tailscale IP):
bind 127.0.0.1 100.64.0.5

# Also uncomment and set a strong password:
requirepass YourVeryStrongPasswordHere

sudo systemctl restart redis
8

Tighten your VPS firewall (UFW)

Now that access goes through Tailscale, you can close PostgreSQL and Redis to the public internet entirely: 

# Allow Tailscale (WireGuard uses UDP port 41641)
sudo ufw allow 41641/udp comment 'Tailscale'

# Keep SSH (but consider changing to a non-standard port later)
sudo ufw allow 22/tcp comment 'SSH'

# Keep HTTPS/HTTP for your web app
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp

# Make sure PostgreSQL and Redis ports are NOT open to the internet
# (they should not be in UFW at all — if they are, remove them)
sudo ufw delete allow 5432
sudo ufw delete allow 6379

# Enable UFW
sudo ufw enable

# Check status
sudo ufw status verbose
✅ What this achieves

PostgreSQL and Redis are now completely invisible to the public internet. Even if an attacker scans your VPS, they will see no open database ports. Only devices connected to your Tailscale network can reach the databases.

5. DIY Option: Self-Hosted WireGuard VPN

If you want full control without relying on Tailscale's servers, here is how to set up WireGuard yourself on your Strato Ubuntu VPS. This is more complex but gives you complete ownership.

⚠️ Before you start

WireGuard configuration mistakes can lock you out of your VPS. Always have an out-of-band access method (Strato's VPS console) before making firewall/network changes. Test in stages — make one change, verify it works.

5.1 — Understanding WireGuard

WireGuard creates a virtual network interface (e.g., wg0) on each machine. Traffic sent to this interface is encrypted with ChaCha20/Poly1305 and sent over UDP. Unlike OpenVPN, WireGuard has no concept of a "client" and "server" — every peer is equal. However, for simplicity, we'll treat your VPS as the "hub" and developer laptops as "spokes."

WireGuard Architecture: Developer 1 Strato VPS (Sweden) wg0: 10.0.0.2/32 ── WireGuard (UDP 51820) ──▶ wg0: 10.0.0.1/24 PostgreSQL: 10.0.0.1:5432 Developer 2 Redis: 10.0.0.1:6379 wg0: 10.0.0.3/32 ── WireGuard (UDP 51820) ──▶ SSH: 10.0.0.1:22 Internet cannot see any of these ports — only WireGuard (51820) is open

5.2 — Install WireGuard on the VPS

# Ubuntu 22.04+ — WireGuard is in the default kernel
sudo apt update
sudo apt install -y wireguard

# Enable IP forwarding (required for VPN routing)
echo "net.ipv4.ip_forward = 1" | sudo tee -a /etc/sysctl.conf
sudo sysctl -p

5.3 — Generate server key pair

# Work in the WireGuard config directory (only readable by root)
cd /etc/wireguard
umask 077

# Generate the server private key and derive the public key
wg genkey | tee server.key | wg pubkey > server.pub

# Save them — you'll need these values
SERVER_PRIVATE_KEY=$(cat server.key)
SERVER_PUBLIC_KEY=$(cat server.pub)
echo "Server public key: $SERVER_PUBLIC_KEY"
ℹ️ Why umask 077?

umask 077 makes all newly created files readable only by root (chmod 600). This is critical — your WireGuard private key must never be readable by other users on the system. Anyone with the private key can impersonate your VPN server.

5.4 — Create server config

# Replace SERVER_PRIVATE_KEY with the actual value from server.key
sudo nano /etc/wireguard/wg0.conf

[Interface]
# The VPN IP for the VPS — all peers connect to this address
Address = 10.0.0.1/24

# WireGuard listens on UDP port 51820
ListenPort = 51820

# Your server's private key (from server.key)
PrivateKey = SERVER_PRIVATE_KEY_HERE

# Save iptables rules when the interface comes up/goes down
PostUp   = iptables -A FORWARD -i wg0 -j ACCEPT; iptables -t nat -A POSTROUTING -o eth0 -j MASQUERADE
PostDown = iptables -D FORWARD -i wg0 -j ACCEPT; iptables -t nat -D POSTROUTING -o eth0 -j MASQUERADE

# ── Peer: Developer 1 ──────────────────────────────────────────
[Peer]
# Developer 1's public key (generated on their machine)
PublicKey  = DEVELOPER1_PUBLIC_KEY_HERE

# This developer's VPN IP — only this IP is allowed from this key
AllowedIPs = 10.0.0.2/32

# ── Peer: Developer 2 ──────────────────────────────────────────
[Peer]
PublicKey  = DEVELOPER2_PUBLIC_KEY_HERE
AllowedIPs = 10.0.0.3/32

5.5 — Generate client key pairs (on each developer machine)

# Run this on the DEVELOPER's machine (not on the VPS)
mkdir -p ~/.wireguard
chmod 700 ~/.wireguard
cd ~/.wireguard

wg genkey | tee client.key | wg pubkey > client.pub
chmod 600 client.key client.pub

echo "Your public key (share this with the VPS admin):"
cat client.pub

5.6 — Create client config (on each developer machine)

# macOS/Linux: create this file at ~/.wireguard/wg0.conf
# Windows: paste into the WireGuard app's "Add tunnel" dialog

[Interface]
# Your VPN IP — unique per developer
Address    = 10.0.0.2/32
PrivateKey = DEVELOPER_PRIVATE_KEY_HERE

# Optional: use VPS as DNS to avoid leaks
# DNS = 1.1.1.1

[Peer]
# The VPS's public key
PublicKey  = SERVER_PUBLIC_KEY_HERE

# VPS's public IP address and WireGuard port
Endpoint   = YOUR_VPS_PUBLIC_IP:51820

# Route ONLY VPN traffic through the tunnel (split tunneling)
# This means only 10.0.0.0/24 goes through WireGuard — everything else uses your normal internet
AllowedIPs = 10.0.0.0/24

# Keep the connection alive (sends a packet every 25 seconds)
# This prevents the tunnel from dropping on NAT firewalls
PersistentKeepalive = 25
ℹ️ What is AllowedIPs?

AllowedIPs = 10.0.0.0/24 tells WireGuard: "Only route traffic to the 10.0.0.0/24 subnet through the VPN tunnel." This is called split tunneling. Your normal internet browsing still uses your regular connection — only database traffic goes through the VPN. If you used 0.0.0.0/0, ALL your traffic would go through the VPS (a full VPN like NordVPN/ExpressVPN — you probably don't want this).

5.7 — Start WireGuard on the VPS

# Start the VPN interface
sudo wg-quick up wg0

# Enable WireGuard to start automatically on reboot
sudo systemctl enable wg-quick@wg0

# Verify it's running
sudo wg show
# You should see "interface: wg0" and a "latest handshake" when a peer connects

5.8 — Start WireGuard on developer machines

# Linux:
sudo wg-quick up ~/.wireguard/wg0.conf

# macOS (via Homebrew): or use the GUI app from wireguard.com
sudo wg-quick up ~/.wireguard/wg0.conf

# Windows: import the config file into the WireGuard GUI app
# Download from: wireguard.com/install

# Test connectivity
ping 10.0.0.1
# Should get replies from the VPS

6. Firewall Hardening with UFW

UFW (Uncomplicated Firewall) is the standard firewall tool for Ubuntu. Here is a complete, hardened UFW setup for your VPS assuming you're using WireGuard: 

# Reset to clean state (WARNING: this removes all existing rules)
sudo ufw --force reset

# Default: deny all incoming, allow all outgoing
sudo ufw default deny incoming
sudo ufw default allow outgoing

# Allow SSH (change 22 to your custom port if you moved SSH)
sudo ufw allow 22/tcp comment 'SSH'

# Allow your web application
sudo ufw allow 80/tcp  comment 'HTTP'
sudo ufw allow 443/tcp comment 'HTTPS'

# Allow WireGuard VPN (if using self-hosted WireGuard)
sudo ufw allow 51820/udp comment 'WireGuard VPN'

# Allow Tailscale (if using Tailscale instead)
# sudo ufw allow 41641/udp comment 'Tailscale'

# PostgreSQL and Redis: DO NOT open to the internet
# They are accessed via VPN only — leave these blocked

# Enable the firewall
sudo ufw enable

# Verify
sudo ufw status verbose
✅ Result after this setup

An external port scan of your VPS will show only ports 22, 80, 443, and 51820 (or 41641 for Tailscale). Ports 5432 (PostgreSQL) and 6379 (Redis) will not appear at all — they are completely invisible to the public internet.

Extra hardening: Move SSH off port 22

Port 22 receives millions of automated brute-force attempts every day. Moving SSH to a non-standard port (e.g., 2222) eliminates 99% of this noise: 

sudo nano /etc/ssh/sshd_config
# Change: Port 22
# To:     Port 2222

# Update UFW first (BEFORE restarting SSH or you'll lock yourself out)
sudo ufw allow 2222/tcp comment 'SSH custom port'
sudo ufw delete allow 22/tcp

# Restart SSH
sudo systemctl restart sshd

# From now on, connect with:
ssh -p 2222 user@your-vps-ip

7. PostgreSQL Security Hardening

7.1 — Create dedicated database users (not superuser)

# Connect to PostgreSQL as the postgres superuser
sudo -u postgres psql

# Create a dedicated user for your app (NOT a superuser)
CREATE USER appuser WITH PASSWORD 'use_a_very_long_random_password_here';

# Grant access only to your specific database
GRANT CONNECT ON DATABASE mydb TO appuser;
\c mydb
GRANT USAGE ON SCHEMA public TO appuser;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO appuser;
GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA public TO appuser;

# Exit psql
\q
ℹ️ Why not use the postgres superuser?

The postgres superuser can do anything — drop tables, read all databases, execute system commands. If your app's connection string is ever leaked, an attacker with a limited appuser can only read/write your app's data. A postgres superuser connection could destroy your entire server.

7.2 — Enforce SSL for all connections (optional but recommended)

# In postgresql.conf:
ssl = on
ssl_cert_file = 'server.crt'
ssl_key_file  = 'server.key'

# In pg_hba.conf, change 'host' to 'hostssl':
hostssl    all    appuser    10.0.0.0/24    scram-sha-256
# This requires SSL even on the VPN — belt and suspenders security

7.3 — Automated security updates for PostgreSQL

# Enable automatic security updates
sudo apt install -y unattended-upgrades
sudo dpkg-reconfigure --priority=low unattended-upgrades

8. Redis Security Hardening

sudo nano /etc/redis/redis.conf

Make these changes:

# 1. Bind only to localhost and VPN interface
bind 127.0.0.1 10.0.0.1
# (or your Tailscale IP: 100.64.0.5)

# 2. Require a strong password
requirepass YourVeryLong64CharRandomPasswordHere

# 3. Disable dangerous commands (optional, high security)
rename-command FLUSHDB   ""
rename-command FLUSHALL  ""
rename-command CONFIG    ""
rename-command DEBUG     ""
rename-command SHUTDOWN  ""

# 4. Set a memory limit (prevents runaway memory usage)
maxmemory 512mb
maxmemory-policy allkeys-lru

# 5. Disable protected mode (it's redundant when using a password + firewall)
protected-mode no

# Restart Redis
sudo systemctl restart redis

# Test the connection with the password
redis-cli -h 127.0.0.1 -a YourPassword ping
# Should return: PONG
⚠️ Generate strong passwords

For both PostgreSQL and Redis, use randomly generated passwords of at least 32 characters. You can generate one with: openssl rand -base64 32
Example output: vK8mNpQr3xYzA1bCdEfGhIjK4lMnOpQr

9. Prisma Connection Strings

After setting up your VPN, update your Prisma connection URL in .env or wherever you store environment variables (never commit these to git): 

# For Tailscale (use your VPS's Tailscale IP)
DATABASE_URL="postgresql://appuser:StrongPassword@100.64.0.5:5432/mydb?schema=public"

# For self-hosted WireGuard (use your VPN IP)
DATABASE_URL="postgresql://appuser:StrongPassword@10.0.0.1:5432/mydb?schema=public"

# With SSL enabled (add ?sslmode=require)
DATABASE_URL="postgresql://appuser:StrongPassword@10.0.0.1:5432/mydb?schema=public&sslmode=require"

Prisma in production (e.g., on Vercel, Render, Railway)

If your app is deployed on a hosting platform, it can't connect to your private VPS unless you either:

  1. Add the hosting platform to your WireGuard/Tailscale network (complex but secure)
  2. Use a connection pooler like PgBouncer with a public-facing port, protected by SSL certificates and strong authentication
  3. Use a managed database (e.g., Supabase, Neon, PlanetScale) for the production database, and keep the VPS database for development only
ℹ️ Recommended for your setup

Since you use the VPS for development/staging with Prisma, and both developers are connecting from their laptops: use Tailscale or WireGuard to give each developer direct access to the database. For a production deployment (if you have one), consider a managed database like Supabase (built on PostgreSQL) which handles all the security infrastructure for you.

10. Final Security Checklist

Go through this checklist when you're done. Print it out and check off each item:

Area Check How to verify
Firewall Only ports 22 (or custom), 80, 443, and VPN port are open sudo ufw status verbose
Firewall Port 5432 (PostgreSQL) is NOT open to the internet nmap -p 5432 your-vps-ip from external machine
Firewall Port 6379 (Redis) is NOT open to the internet nmap -p 6379 your-vps-ip from external machine
VPN WireGuard or Tailscale is running and auto-starts on reboot sudo systemctl status wg-quick@wg0
VPN Both developers can ping the VPS VPN IP ping 10.0.0.1 from each laptop
PostgreSQL App connects as a limited user, not postgres superuser Check your DATABASE_URL — username should not be postgres
PostgreSQL Password uses SCRAM-SHA-256 (not MD5) SELECT usename, passwd FROM pg_shadow; — should start with SCRAM-
Redis Redis has a strong requirepass set redis-cli info server | grep requirepass
Redis Redis is NOT bound to 0.0.0.0 ss -tlnp | grep 6379 — should NOT show 0.0.0.0:6379
SSH Password authentication is disabled in SSH grep PasswordAuthentication /etc/ssh/sshd_config → should be no
SSH Root login is disabled grep PermitRootLogin /etc/ssh/sshd_config → should be no
Secrets No secrets in git history git log -S "password" --all — should return nothing
Updates Automatic security updates are enabled cat /etc/apt/apt.conf.d/20auto-upgrades

Disable SSH password authentication (important!)

sudo nano /etc/ssh/sshd_config

# Set these values:
PasswordAuthentication no
PermitRootLogin no
PubkeyAuthentication yes

# Restart SSH (make sure you still have your key loaded first!)
sudo systemctl restart sshd
