# Kollegan ERP: AI-Native Refactor And ISO/IEC 27001:2022 Readiness Plan

Kollegan is an ERP platform. The refactor must make the codebase easier for humans and AI agents to maintain while producing evidence useful for ISO/IEC 27001:2022 readiness.

This plan has two goals:

- Engineering: cleaner architecture, API-first workflows, mobile-ready UI, stronger branding/theming, fewer monoliths, and better AI support.
- Governance: safer change control, production-data protection, documented security processes, auditable release practices, and ISO readiness evidence.

This plan supports ISO/IEC 27001:2022 readiness, but certification still depends on operating the company-wide ISMS over time.

## Core Principles

- Existing business data is production data.
- Architecture may change aggressively; production data must not be destroyed.
- Kollegan is the ERP. Demos are isolated demos.
- Browser UI and future mobile clients must use HTTP APIs.
- Prisma access stays inside repositories.
- Public offer, signing, PDF, project, company, product, auth, and user flows are critical.
- AI agents must follow the same project rules as human engineers.
- ISO evidence should be generated by the engineering process, not added as fake paperwork later.

## Implementation Order

1. ISO readiness baseline docs.
2. AI rules, docs proxies, and skills.
3. Production data safety docs and migration scanner.
4. Feature flag foundation.
5. Docs inventory and rewrite.
6. Render and API contract test baseline.
7. `/api/v1` wrappers and feature API clients.
8. Branding and theme resolver.
9. Public offer page split behind feature flag.
10. Offerter dashboard split.
11. Document/PDF generator split.
12. Product library split.
13. Companies split.
14. Projects split.
15. Templates split.
16. Settings/sidebar/dashboard shell split.
17. Dead-code cleanup PRs.
18. Dependency and file-size enforcement.

## Hard Acceptance Criteria

- No production data is lost.
- Existing offer/signing flows still work.
- Projects, companies, products, users, and auth still work.
- `/api/v1` exists and is used by new clients.
- Legacy API paths are managed through compatibility wrappers or retired after evidence.
- Branding has platform, organization, company, document, and user precedence.
- Frontend has consistent layout, density, breakpoint, and component ownership rules.
- Dead files are inventoried before deletion.
- Confirmed junk files are removed in cleanup PRs.
- No hand-written production source file above 1000 lines remains without an approved exception.
- CI blocks new or modified 1000+ line hand-written production files.
- Docs are current.
- AI agents have consistent project instructions.
- Demos are isolated from ERP architecture.
- Security docs exist and link to engineering evidence.
- ISO readiness gaps are visible rather than hidden.

## Feature Flag Foundation Acceptance Criteria

- Feature flags are tenant-scoped by `organizationId` and environment.
- Release flags require an owner and expiry date.
- Flag create/update/delete operations create audit events.
- Browser clients use `/api/v1/feature-flags`.
- Legacy `/api/feature-flags` wrappers exist only for compatibility during API v1 migration.
- Public-offer rewrite work must use this foundation instead of hard switching customers onto a new renderer.
